# Stand-Up Indulgent Gathering on Lines

Interactive companion to *A Visibility vs. Memory Trade-off for Stand-Up Indulgent Gathering on Lines*. This project translates the three numbered algorithms in the journal manuscript. It uses the shared Simulant viewer for executions, adversary branches, the configuration graph, algorithm explanations and the model/source view.

| Simulation | Paper | Visibility | Initial parity |
| --- | --- | --- | --- |
| `standup-gathering-h-plus-three` | Algorithm 1, oblivious | φ ≥ max(4, H_init + 3) | odd O_init or odd M_init |
| `standup-gathering-h-plus-one` | Algorithm 2, oblivious | φ ≥ max(4, H_init + 1) | odd O_init |
| `standup-gathering-two-colors` | Algorithm 3, two colors | φ ≥ max(1, H_init) | odd O_init or odd M_init |

H_init is the maximum distance between neighboring occupied nodes, O_init counts distinct occupied nodes, and M_init includes both borders. These are assumptions on the initial configuration; the robots do not know them. The robots are anonymous, disoriented and fully synchronous. The oblivious algorithms have one color; Algorithm 3 starts every light at X and uses X/Y, with Z meaning both colors on one node.

```bash
# From the workspace root
pnpm --filter @bramas/simulant-project-standup-gathering dev
pnpm --filter @bramas/simulant-project-standup-gathering build
pnpm cli check-config -p standup-gathering-two-colors -s '{"positions":[0,2,4],"phi":2}'
pnpm cli check-all -p standup-gathering-h-plus-one
node --import tsx --import ./packages/vite-plugin/src/register.ts --test --test-isolation=none tests/standup-gathering.test.ts
```

Select an algorithm in the top bar and load a saved example. The crash presets include recorded executions: border and partial crashes occur in round 1, and the interior crash occurs in round 2. Round 0 is the initial configuration. Step through a preset to replay its crash and subsequent gathering, or choose other adversary branches. In the luminous partial-crash preset, the crash happens after Compute: one robot keeps its new Y light at the crash coordinate while another moves. The luminous drawing uses blue for X and orange for Y, keeping the paper’s letters; a node containing both is Z. Red crosses identify crashed robots in the drawing; robots cannot sense those marks. The presets cover fault-free gathering, border and interior crashes, an even occupied count with odd span, and an initial multiplicity that permits partial crashes. The only editable settings are visibility φ and the initial coordinates. The settings take one coordinate per robot, so `[0,0,1,2]` places two robots at coordinate 0. Coordinates are sorted by the adapter. Visibility is chosen initially from the algorithm's bound and can be edited. The `.sim` definitions report violated visibility/parity assumptions while allowing runs outside the theorem's scope. Their `where` predicates accept arbitrary valid configurations, including multiplicities, larger hulls and larger visibility; starting configurations and finite check settings are supplied separately in `src/projects.ts`. Parity counts distinct occupied nodes, not individual robots; an even border distance is equivalent to odd M_init.

## Encoding the paper's model

`sim/model.sim` supplies a radius-φ sensor, external lights, crashes and the permanent gathering goal. `sim/h-plus-three.sim`, `sim/h-plus-one.sim` and `sim/two-colors.sim` retain the paper's rule order. Each guard is checked in both orientations before choosing the earliest matching rule. A symmetric directional match is resolved by the adversary's frame, independently for each robot. The sensor returns color sets, never multiplicities, identities, crash flags, the population or the size of the encoding.

The semantic core currently has ring topologies. This project encodes the occupied interval of the infinite line in a ring, shifted by φ + 1, with empty padding at both ends. All three algorithms move inside the initial occupied hull. The adapter computes `N = max(64, max(positions) + 2φ + 3)` so radius-φ views cannot see across the padding. It hides only N from the settings form, computing it from the visible settings. The check settings in `src/projects.ts` compute N using the same adapter; the general N predicate accepts larger sizes. The coordinate domain checks population, ordering and parity. The φ domain uses `requiredVisibility`: max(4, H_init + 3) for Algorithm 1, max(4, H_init + 1) for Algorithm 2, and max(1, H_init) for Algorithm 3. It also uses `fitsLine` to check the encoding’s padding. Both the default radius and the warning’s required value come from that same `.sim` definition. Too-small visibility, including φ < 4 for the oblivious algorithms, produces an advisory warning naming φ and its required value; execution remains available. Guards cannot match nodes outside the observed view, so experimenting with smaller radii does not cause indexing errors. Structurally invalid settings are reported inline without console errors. The full configuration graph consequently describes this finite encoding. It does not prove the unbounded theorem about the infinite line.

Crashes are adversary choices, with no crash-enable or crash-location parameters. At each phase the adversary chooses a subset of correct robots. They must be colocated with each other and with every already-crashed robot. The first nonempty choice therefore fixes the crash location for the rest of that execution. The empty choice remains available forever, including fault-free executions. A robot can crash before Look or after Compute and before Move; crashes after an atomic move are represented before the next Look. Crashed robots stay visible and immobile. The task includes them and checks **eventually always gathered**. Preset coordinates and crash rounds select recorded branches and do not restrict the model.

Algorithms 1 and 2 use `LineRobots`, an occupancy-only sensor with no light storage, slots, or light actions. Algorithm 3 uses `LuminousRobots`, whose lights always start at X. Its component-owned Boolean list is initialized directly from the coordinate list, with no initial-light parameter. Immutable simulator slots associate lights with robots without exposing identities. Color updates run in `beforeMove` alongside the crash component, so a Compute-phase light change persists when a crash prevents movement. Both algorithm memory and public state remain Unit.

`src/projects.ts` supplies the settings adapter and presets; `src/renderer.ts` draws the line, external lights, multiplicities and crashed robots using the drawing theme. The page and graph worker share the same registry. The public website includes this project through its explicit public-project list; no publication or deployment is performed by creating it.

Checks filter the finite settings supplied by `src/projects.ts` through the model domain predicates, then explore every reachable adversary branch, subject to the experiment's state/depth limits. They are evidence for the translation rather than a proof of the paper. Tests additionally compare both two-color examples and the Algorithm 1 example against the manuscript figures, check Algorithm 2’s false-border recovery, and distinguish the two crash phases. The Algorithm 2 illustration disagrees with its formal four-block rules after its first three transitions: the showcase follows the formal rules and proof prose.
